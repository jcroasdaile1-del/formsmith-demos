# Private Piano Studio Apps Script backend

This folder contains the Google Apps Script persistence layer for the private piano-studio application. It is designed for a **container-bound** Apps Script project attached to the Google Spreadsheet that will hold the studio records.

`Index.html` is generated from the portfolio UI and is ready to paste into an Apps Script HTML file named `Index`.

## Files

- `Code.gs` — web-app entry point, setup/migrations, validation, reads, and writes.
- `Code.contract.test.cjs` — Node contract tests with an in-memory Apps Script/Sheets mock.
- `appsscript.json` — V8 manifest with Spreadsheet and container-UI scopes.
- `Index.html` — generated application UI with automatic `google.script.run` persistence.
- `../build-appscript-version.mjs` — copies the canonical UI into this folder.

## Set up the bound spreadsheet

1. Create or open the Google Spreadsheet that should own the private studio data.
2. Open **Extensions → Apps Script** from that spreadsheet. Do not create a standalone script.
3. Copy `Code.gs` into the script project.
4. In Apps Script project settings, enable the manifest file and copy `appsscript.json`.
5. Copy `Index.html` into an Apps Script HTML file named `Index`.
6. Run `setupStudio()` once from the editor and approve the requested permissions. This binds the project to that spreadsheet in private Script Properties.
7. Reload the spreadsheet. The **Piano Studio** menu can open the app or rerun the idempotent setup/migration.

Setup obtains the container with `SpreadsheetApp.getActiveSpreadsheet()`. Apps Script web requests do not receive an active container, so deployed requests reopen the setup-time spreadsheet ID from Script Properties. The ID is never hardcoded or returned to the browser. The code contains no deployment URL, Drive folder, or external service URL.

After changing the canonical portfolio UI, regenerate the Apps Script file from the repository root:

```bash
node piano-studio/build-appscript-version.mjs
```

## Private deployment

The manifest defaults the web app to:

- execute as the deploying user;
- access by the deploying user only (`MYSELF`);
- the Spreadsheet scope required for `openById` during web-app requests;
- no Drive scope;
- no `XFrameOptionsMode.ALLOWALL`.

The Spreadsheet scope can technically access files available to the deploying account, but this code opens only the ID captured from its bound sheet. For a solo teacher, keep access set to **Only myself**. If the owner deliberately needs to share the app inside a managed Google Workspace domain, change deployment access in the Apps Script deployment UI only after reviewing that domain’s policy. The application has no public booking portal and should not be deployed anonymously.

## Client API

All public functions are suitable for `google.script.run`.

### `loadStudio()`

Returns all collections, nested settings, `schemaVersion`, and `loadedAt` in one round trip:

```js
google.script.run
  .withSuccessHandler(function (state) {
    StudioStore.hydrate(state);
  })
  .withFailureHandler(showSaveError)
  .loadStudio();
```

### `saveRecord(collection, record)`

Creates or updates one record by `record.id`. A missing ID is generated by the server. Existing records retain their original `createdAt`; every accepted change receives a server `updatedAt`. The response is `{ ok, collection, record, state }`; `state` is the canonical prospective state accepted under the write lock.

```js
google.script.run
  .withSuccessHandler(function (result) {
    StudioStore.upsert(result.collection, result.record);
  })
  .withFailureHandler(showSaveError)
  .saveRecord('students', student);
```

IDs are strings and must use only letters, numbers, `.`, `_`, `:`, or `-`. Spreadsheet row numbers are never accepted as identifiers.

### `deleteRecord(collection, id)`

Deletes an allowed record by ID only when no other record references it. It never cascades silently.

The response is `{ ok, collection, id, state }`. Completed repertoire, completed recitals and their participants, and converted inquiries are retained even though their collections otherwise permit deletion.

Deletion is rejected for:

- lessons;
- assignments;
- tuition charges;
- payments;
- makeup credits;
- activity.

Use lifecycle states such as cancelled, void, expired, or waived so history remains auditable.

### `saveSettings(settingsPatch)`

Deep-merges a nested settings patch and returns the normalized nested settings object.

### `saveStudioCollections(state, collections)`

Validates and saves several related collections under one script lock:

```js
google.script.run
  .withSuccessHandler(function (result) {
    StudioStore.hydrate(result.state);
  })
  .withFailureHandler(showSaveError)
  .saveStudioCollections(
    state,
    ['lessons', 'assignments', 'repertoire', 'makeupCredits']
  );
```

Every selected collection is validated before the first data write. The backend checks IDs, types, required fields, references, immutable financial fields, and cross-record student ownership. It takes formula-aware snapshots of every selected sheet and restores them if a later selected-sheet write fails.

Apps Script and Sheets do not offer a database transaction primitive, so this is a lock-protected, best-effort transaction with rollback. Keep batches focused on the collections involved in one workflow.

`settings` may be included in the selected collection list.

### `reactivateRepertoire(repertoireId)`

Creates a new current repertoire row from a completed source while leaving the
completed row immutable. The successor keeps a `reactivatedFromId` link to the
source. Its exact signature is:

```js
reactivateRepertoire(repertoireId)
// => { ok: true, record, activity, state }
```

This is intentionally a dedicated server action rather than a generic status edit.
It rejects non-completed sources and duplicate current copies of the same piece.

### `resetStudio(seedState, confirmationToken)`

Reset is deliberately difficult to invoke accidentally. It requires:

1. every collection array;
2. nested `settings`;
3. the exact confirmation token `RESET HARMONY HOUSE`.

```js
google.script.run
  .withSuccessHandler(function (result) {
    StudioStore.hydrate(result.state);
  })
  .withFailureHandler(showSaveError)
  .resetStudio(seedState, 'RESET HARMONY HOUSE');
```

The reset runs under the same lock, validation, reference checks, snapshots, and rollback behavior as a multi-collection save.

## Serialization

- Text, dates, times, and ISO timestamps are stored as text.
- Numbers are stored as Sheet numbers.
- Booleans are stored as Sheet booleans.
- Arrays and objects are stored as validated JSON.
- Nested settings are flattened into `Setting Path` rows and reconstructed by `loadStudio()`.
- Formula-like user text is escaped before it reaches a cell.
- IDs and timestamps remain strings, avoiding numeric precision and timezone drift.

## Migration behavior

Setup and every API bootstrap call check the stored schema version.

- Missing tabs are created.
- Recognized legacy key-style headers are renamed to the canonical human-readable header.
- Missing canonical headers are appended to the right.
- Existing rows are not cleared or reordered.
- Unknown user-added columns remain in place.
- Updates preserve unknown cells and formulas for the same record ID.
- A same-named sheet containing wholly unrecognized data causes setup to stop instead of overwriting it.
- A spreadsheet created by a newer schema version is rejected rather than downgraded.

Before making a future breaking schema change, increment `STUDIO_SCHEMA_VERSION` and add an additive case to `runVersionMigrations_()`.

## Historical and financial safety

- Activity rows are append-only.
- Lesson, assignment, tuition, payment, makeup, completed repertoire, and completed recital history cannot be removed or rewritten through normal or bulk saves.
- Final-state validation requires every minor to retain a guardian, exactly one lesson subject (`studentId` or `inquiryId`), no overlapping active recurring slots, at most one active slot per student, unique schedule/date occurrences, coherent inquiry conversion links, and synchronized makeup-credit redemption.
- Current assignments can move to `Previous`, `Completed`, or `Cancelled`; after that, their archival row is read-only. Completed recital participants carry student/piece snapshots and are frozen with the completed recital.
- Converted inquiries and terminal makeup credits cannot be reopened by stale client data. A completed trial may change ownership only as part of the same validated inquiry-conversion transaction.
- Core financial identity fields on charges and payments are immutable after creation. A mistaken transaction can be marked `Void` with a reason and timestamp; void records cannot be reopened or rewritten.
- Student, guardian, schedule, repertoire, and recital deletion is blocked while referenced.
- Writes use `LockService.getScriptLock()` to prevent overlapping web-app saves.
- The server validates the payload independently of browser validation.

Every mutating workflow still performs one complete pre-read under the lock. That read is necessary because references, schedule collisions, stale archival transitions, inquiry conversion, and makeup redemption can span collections that were not selected for writing. Successful record, delete, batch, reactivation, and reset responses are built from the already-validated prospective state, avoiding a redundant full post-write read.

Locks serialize each request, but collection replacement does not provide multi-tab optimistic versioning for mutable rows. Treat the app as a single-teacher workspace, avoid editing the same collection in two tabs at once, and hydrate the canonical `result.state` returned by collection saves.

The frontend should always attach both `.withSuccessHandler(...)` and `.withFailureHandler(...)`, disable duplicate submissions while a call is pending, and show a business-readable error message from the failure handler.

## Backend contract tests

From `formsmith-demos`, run:

```bash
npm run test:piano-backend
```

The suite executes the real `Code.gs` in Node with mocked Apps Script services and an in-memory spreadsheet. It covers setup/web binding, full reset, cross-record validation, lifecycle transitions, idempotent conversion, repertoire reactivation, formula-safe round trips, canonical response state, and injected multi-sheet rollback.
